โค้ดคือวิธีทำ หน้านี้คือเหตุผล ย่อมาจาก `docs/design.md` ใน repo ซึ่งเป็นฉบับเต็ม การตัดสินใจในนั้นเปลี่ยนได้เมื่อมีหลักฐานเท่านั้น และต้องบอกว่าหลักฐานคืออะไร

## ปัญหา

Claude Code หนึ่ง session ใน repo นี้ทำงานแทนเจ้าของ มันต้องรู้ประชุม งาน และโปรเจกต์ของเจ้าของตั้งแต่วินาทีแรก ตัดสินใจแบบที่เจ้าของจะตัดสิน ทำงานใน repo อื่นได้โดยไม่ชนกับ session ที่เจ้าของเปิดอยู่ และถามก่อนทำทุกอย่างที่เจ้าของยังไม่ได้มอบให้

ใครก็ clone repo แล้วได้ agent ของตัวเอง ไม่มีอะไรของเจ้าของคนก่อนติดมาด้วย

## ชั้นต่างๆ

| ชั้น | อยู่ที่ | ของใคร |
|---|---|---|
| ตัวตน คุณเป็นใคร ตัดสินใจอย่างไร เส้นห้าม ระดับสิทธิ์ต่อหมวด | `profile/mode/SKILL.md` ลิงก์ไปที่ `~/.claude/skills/<ชื่อ>-mode` | เจ้าของ `onboard` เขียน `improve` ปรับ |
| วิธีทำงานโค้ด | pstack ถ้าติดตั้งไว้ ถ้าไม่มีใช้กฎสั้นใน `lib/contract.ts` | ไม่บังคับ |
| engine คือ collector, brief, โน้ต, journal, การส่งงาน และ guard | repo นี้ | ทุก clone ใช้ร่วมกัน |
| ของที่เจ้าของเพิ่มเอง | `profile/commands/`, `profile/collectors/`, `profile/skills/`, `profile/CLAUDE.md` | เจ้าของ agent เขียนเมื่อขอ |

ตัวตนไม่ใช่โค้ดและไม่ได้แชร์ การเก็บไว้ใน `profile/` ข้าง engine และไม่ใส่ใน git ทำให้ `git pull` ครั้งเดียวอัปเดต engine ได้โดยไม่แตะตัวตนของใคร backup สร้าง commit บน ref ของมันเอง `refs/twin/backup` ซึ่งไม่ใช่ branch จึงไม่มี branch ไหนพาไฟล์ส่วนตัว `git push --all` ส่งมันออกไปไม่ได้ และ branch ที่ checkout อยู่ไม่เคยแยกจาก template

ของที่เจ้าของเพิ่มเองอยู่ใน `profile/` ด้วยเหตุผลเดียวกัน ถ้าไม่มีที่นี้ เจ้าของที่อยากได้คำสั่งของตัวเองต้อง fork engine และทุกครั้งที่ pull จะชนกัน

วิธีทำงานโค้ดเป็นของไม่บังคับ เพราะเจ้าของส่วนใหญ่ไม่ใช่วิศวกร การวัดบนงานโค้ด (fixture repo 5 ตัวที่มี hidden test, setup ละ 10 รอบ) พบว่า agent ตัวเดียวที่มีกฎวิธีทำงานสั้นๆ ถูกพอๆ กับ agent ที่ใช้ method skill เต็มพร้อม subagent ในราคาราวครึ่งเดียว กฎสั้นจึงเป็นทางเลือกจริง ไม่ใช่โหมดที่ด้อยกว่า และไม่มีอะไรพังเมื่อไม่มี pstack

## รู้จักคนทั้งคน

การตัดสินใจเป็นหนึ่งในหกด้าน คือ ตัวตน เครื่องมือ งาน ชีวิตนอกงาน วิธีที่อยากให้ช่วย และวิธีตัดสินใจ onboard แตะทุกด้านแบบเบาๆ ในวันแรก จากนั้น brief ถามวันละ 1-3 ข้อจากด้านที่ตื้นที่สุด

การสัมภาษณ์ยาวแค่ไหนขึ้นกับประวัติ มีการเทียบสามแนวทาง คือถามคำถามยาก ขุดจากหลักฐาน และเรียนจากงานที่เกิดขึ้นจริง แต่ละทางพลาดในจุดที่อีกทางทำได้

- เส้นห้าม สิทธิ์ เหตุการณ์ใหญ่ที่นานๆ เกิด และกฎแบบมีเงื่อนไข ไม่เคยโผล่ในหลักฐาน จึงต้องถาม
- คนตอบในแบบที่อยากเป็น หลักฐานช่วยแก้ เจ้าของคนก่อนของ engine นี้ไม่เคยบอกในการสัมภาษณ์ว่า agent ถามมากไป แต่การนับคำตอบของเขาแสดงให้เห็น
- การตัดสินใจที่เกิดบ่อย เรียนได้ดีที่สุดด้วยการเดาก่อนที่เจ้าของจะตัดสิน

ดังนั้นถ้ามีประวัติที่ยินยอมให้อ่านเยอะ onboard ขุดกฎก่อนแล้วให้เจ้าของยืนยันทีละข้อพร้อมคำพูดเดิม ถ้ามีน้อยก็สัมภาษณ์ชุดละ 5 ข้อ คำตอบที่ขัดกับประวัติถูกถามพร้อมหลักฐาน ประวัติไม่ได้ชนะเสมอไป

collector `history` เก็บเฉพาะคำของเจ้าของเอง ทิ้ง prompt ของ worker, subagent, สรุปตอน compact และบรรทัดของระบบ และปิดรูปแบบ secret ที่คนมักวางลงไป การปิดใช้รายการ pattern จึงลดความเสี่ยงได้แต่สัญญาไม่ได้ว่าไม่หลุดเลย

ตัวตนเก็บเป็นไฟล์ที่มีรูปแบบ ทุกหมวดเริ่มที่ "ถามก่อน" สิทธิ์ให้ทีละหมวด ระดับขึ้นเฉพาะเมื่อเจ้าของบอก และลดหนึ่งขั้นหลังพลาดหนัก เส้นห้ามชนะทุกระดับ ตัวตนโหลดเป็นข้อความ ไม่ใช่การเรียก skill เพราะในทางปฏิบัติคำสั่งให้เรียก skill ถูกข้ามบ่อยพอที่จะเชื่อไม่ได้ SessionStart hook จึงพิมพ์ mode ทั้งหมดใส่ทุก session รวม worker

## collector

`collectors/*.ts` ถูกค้นจากโฟลเดอร์ โฟลเดอร์คือรายการเดียว แต่ละตัวประกาศ `defaultOn` และสิ่งที่มัน `requires` profile เก็บเฉพาะสิ่งที่เจ้าของเลือกเอง ตัวที่ไม่ได้ตั้งจะเปิดเมื่อ `defaultOn` เป็นจริงและเงื่อนไขครบตอนนั้น ตั้ง devRoot ทีหลัง `projects` ก็เปิดเอง และ brief ไม่เตือนเรื่องแหล่งที่เจ้าของไม่มี

แต่ละตัวรันใน child process ของตัวเองและโดนหยุดเมื่อเกินเวลา brief คือการเรียงลำดับเดียวจากเรื่องที่ต้องดูของทุก collector ตัดให้พอดีความยาว `todo` พิมพ์ทั้งหมด สองอย่างนี้จึงขัดกันไม่ได้

มีแค่ `radar` ที่เรียก model เบื้องหลัง วันละครั้ง และเฉพาะหลังเจ้าของบอกว่าสนใจอะไร journal ดึงตามจริง จึงไม่เสียค่าอะไรและแต่งเรื่องไม่ได้

## การส่งงาน

- worktree สร้างจาก `origin/develop` (ถ้าไม่มี ใช้ default branch) บน branch `<ชื่อ agent>/<slug>` worker แต่ละงานได้ port ของตัวเอง
- การกัน push เป็นโครงสร้าง ไม่ใช่กฎในข้อความ `pre-push` hook ของแต่ละ worktree ให้ push ได้เฉพาะ branch ของงานนั้น gate อื่นเป็น deny rule ในไฟล์ settings ที่สร้างใหม่ทุก turn production ไม่มี gate จึงอนุมัติผ่านการส่งงานไม่ได้
- commit นับจาก `git log` ไม่ใช่จากที่ worker บอก รายงานที่อ่านไม่ได้ไม่มีวัน "เสร็จ"
- turn ที่บอกว่าเสร็จได้ turn ตรวจหนึ่งครั้ง เมื่อแก้ UI แต่ไม่ได้กด หรือแก้โค้ดแต่ไม่ได้ลอง input เพราะกฎที่เขียนเป็นข้อความไม่ได้หยุด UI ที่ไม่มีใครกดไม่ให้ถึงมือเจ้าของ และ worker ทุกแบบที่วัดรายงานว่างานแบ่งบิลเสร็จโดยไม่ได้ตรวจ input
- งานรันพร้อมกันได้ไม่เกิน `maxRuns` (ค่าเริ่ม 3) เพราะการรันหลาย worker พร้อมกันเป็นเรื่องของเครื่องและแพ็กเกจของเจ้าของ ไม่ใช่ของ engine
- งานเป็นของ session ที่ส่งมัน เพราะเมื่อเปิดหลายหน้าต่าง งานจากหน้าต่างหนึ่งเคยไปโผล่ในทุกหน้าต่าง

ขนาดใน brief คือความลึกของการรีวิว เล็กไม่มีรีวิว กลางและใหญ่มี reviewer อิสระหนึ่งตัวดู diff สุดท้าย ตัวเลขที่ใช้ตัดสิน มาจาก fixture ที่ยากกว่า 5 ตัว (cache dedupe พร้อม error caching, การถอด path ที่มี traversal, การปัดเศษตอนแบ่งบิล, parser ระยะเวลาที่มี edge case ที่ไม่ได้บอก และ migration 15 ไฟล์) setup ละ 3 รอบ

| setup | hidden test ผ่าน | blind judge เลือกเป็นอันดับแรก |
|---|---|---|
| agent ตัวเดียว | 93.5% | 5 จาก 30 |
| agent ตัวเดียว + reviewer หนึ่งตัว | 93.5% | 15 จาก 30 |
| pstack poteto-mode ตามที่เขียน | 87.6% | 10 จาก 30 |

poteto-mode ใช้เวลาราวสามเท่า

## วัดจริง ไม่เดา

ตัวเลขที่ improve ทำเพื่อมัน คือ **สัดส่วนงานที่ส่งไปแล้วเจ้าของไม่ต้องแตะอีกเลย** หมายถึงไม่มี follow-up จากเจ้าของนอกจากการอนุมัติหรือการตรวจที่ engine ขอเอง นับเมื่องานปิดแล้วหรือผ่านไป 12 ชั่วโมงหลัง turn สุดท้าย นับจาก `runs/` ไม่ได้ให้ model ตัดสิน และวัดสิ่งที่เจ้าของจ้าง agent มาทำ ตัวเลขนี้มีขอบที่รู้อยู่ เช่น การอนุมัติที่แนบคำแก้มาด้วยนับว่าไม่แตะ และงานที่ปิดโดยทิ้งงานไปก็นับว่าไม่แตะ

eval ไม่ใช่ตัวเลขนี้ มันเป็นราวกั้นไม่ให้ improve ทำของพัง เพราะ eval ที่ให้ model ตัดสินมีความผันผวน บน twin จริง สถานการณ์เดียวกันผ่านในรอบหนึ่งแล้วตกในรอบถัดไปโดยไม่มีอะไรเปลี่ยน

- ทุก commit ที่ขึ้นต้นด้วย `improve:` ผ่าน gate ชั้นเร็ว ซึ่งกันเฉพาะสิ่งที่ตรวจได้แน่นอน เช่น กฎหลักหายจากสัญญาของ worker, `bun test` ตก, ไฟล์ตัวตนอ่านไม่ได้ หรือ fixture ที่ HEAD ผ่านเต็มตกลงสองรอบติด
- วัดบน twin จริง improve ที่แก้แค่ profile ใช้ 51, 52 และ 55 วินาที การแก้ engine ใช้ 66 วินาที การปฏิเสธเพราะกฎหายหรือไฟล์ตัวตนเสียใช้ 0.06 ถึง 0.08 วินาที
- ตัวอย่างจริงสองครั้ง การเพิ่มกฎสองข้อวัด replay ได้ 10/14 เป็น 11/14 แล้ว commit ผ่าน ส่วนการลบกฎ input ออกจากสัญญา ทำให้ arms ตกจาก 100% เป็น 83% (split-bill จาก 9/9 เป็น 6/9 ทั้งสามรอบ) และ hook ปฏิเสธ commit พร้อมบอกชื่อ split-bill
- ชุดเต็ม `bun twin.ts eval full` รันเมื่อเจ้าของสั่งเท่านั้น ใช้เวลาหลายสิบนาที ไม่ได้ตั้งเวลาและไม่ขึ้นใน brief เคยมีการรันชุดเต็มทุกคืนพร้อมแจ้งใน brief แล้วเจ้าของตัดสินใจเอาออก

## สิ่งที่ตั้งใจไม่ทำ

- ไม่มี daemon ไม่มี MCP server ไม่มีฐานข้อมูลหรือ embedding
- ไม่เรียก model เบื้องหลัง ยกเว้น `radar` และ worker ที่ร่าง plan ตอนเช้า
- ไม่เขียนลง repo อื่น ยกเว้น worker บน branch `<ชื่อ agent>/*`
- ไม่ push ข้อมูลของเจ้าของไปที่ไหน นอกจาก remote `backup` ของเจ้าของเอง
- `daily` ปิดงานที่ merge แล้วเสมอ เพราะ twin สร้างมันเอง แต่ลบ build output ใน repo ของเจ้าของเฉพาะเมื่อเปิด `autoClean` เพราะในโฟลเดอร์ของคนอื่น คำว่า "สร้างใหม่ได้" เป็นแค่การเดา
- ไม่แสดงเงินที่ไหนเลย การใช้งานอยู่บน subscription และตัวเลขเป็นดอลลาร์ถูกอ่านเป็นบิล

## สิ่งที่ยอมแลก

- worker ที่รันแบบไม่มีหน้าจอถามกลางงานไม่ได้ แลกกับการอนุมัติได้จากทุกที่ และเข้าไปทำต่อเองได้ด้วย `claude --resume <id>` ใน worktree
- แหล่งข้อมูลภายนอกอาจช้าได้ถึง 10 นาที brief บอกว่าเก่าแค่ไหน และ `sync <ชื่อ>` ดึงใหม่ได้ในคำสั่งเดียว
- worktree ต่องานกินพื้นที่ดิสก์ แลกกับงานที่ไม่ชนกันเลย และ `clean` ลบตัวที่ merge แล้ว
