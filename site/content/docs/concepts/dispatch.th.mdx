agent ไม่แก้ไฟล์ในโปรเจกต์อื่นเอง guard hook ห้ามไว้ งานโค้ดทุกชิ้นไปทาง worker ซึ่งคือ `claude -p` ที่รันแบบไม่มีหน้าจอ ในสำเนาแยกของโปรเจกต์นั้น การส่งงานจึงต้องมีคำสั่ง `claude` ในเครื่อง

## งานหนึ่งชิ้นทำงานอย่างไร

<RunFlow lang="th" />

<Steps>
  <Step>
    **เขียน brief** agent อ่านสถานะโปรเจกต์ `CLAUDE.md` ของโปรเจกต์ และไฟล์ที่งานแตะ แล้วเขียน brief เป็นภาษาไทย บรรทัดละประโยค สิ่งที่เดาเองมีป้าย `[เดา]` กำกับ
  </Step>
  <Step>
    **ส่ง** `bun twin.ts dispatch <project> <slug>` สร้าง worktree จาก `origin/develop` (ถ้าไม่มี ใช้ default branch) ที่ `<repo>/.claude/worktrees/<ชื่อ agent>-<slug>` บน branch `<ชื่อ agent>/<slug>` คัดลอกไฟล์ `.env*` ที่ root ไปให้ และให้ port ว่างตั้งแต่ 4101 ขึ้นไปเป็น `TWIN_PORT`
  </Step>
  <Step>
    **worker ทำงาน** ด้วย `CLAUDE.md` และ skill ของโปรเจกต์ ตัวตนของคุณจาก SessionStart hook และสัญญาการทำงานของ worker ระหว่างนั้นคุณคุยเรื่องอื่นกับ agent ต่อได้
  </Step>
  <Step>
    **รายงาน** worker ตอบเป็น JSON ตาม schema agent สรุปว่าทำอะไร ตรวจอะไร กดอะไรแล้ว ลองอะไรแล้ว commit กี่ตัว และเหลืออะไร แล้วถามคุณหนึ่งเรื่องที่ต้องตัดสินใจ
  </Step>
</Steps>

ตัวอย่าง brief ที่ agent ส่ง

```text title="brief"
ชนิด: bug
ขนาด: เล็ก
เป้าหมาย: ลูกค้ากดปุ่มชำระเงินบน iOS Safari แล้วไปหน้าจ่ายเงินได้
อ้างอิง: src/checkout/Button.tsx
ห้าม: ไม่เพิ่ม dependency
เสร็จเมื่อ: เปิดหน้า checkout ใน iOS Safari กดปุ่มแล้วไปหน้าจ่ายเงิน
ลงที่: push branch อย่างเดียว
อาการ: กดปุ่มแล้วไม่มีอะไรเกิดขึ้น เฉพาะบน iOS Safari [เดา]
คงไว้: Chrome บน desktop ยังจ่ายเงินได้เหมือนเดิม
```

แต่ละชนิดงาน (`bug`, `ui`, `feature`, `design`, `build`, `plan`, `release`, `deps`, `ci`, `feel`) ต้องมีบรรทัดของตัวเอง และมีความหมายของ `เสร็จเมื่อ` ของตัวเอง `dispatch` ปฏิเสธ brief ที่ขาดชนิดหรือมีบรรทัดว่าง และบอกว่าขาดบรรทัดไหน brief บอกว่าทำอะไร ให้ใคร อะไรต้องคงไว้ และข้อจำกัด ไม่บอกวิธีทำ

agent ส่งเลยโดยไม่รอ เว้นแต่มี `[เดา]` ที่ถ้าผิดต้องทำใหม่เกือบหมด หรืองานแตะเส้นห้ามหรือหมวดที่ระดับสิทธิ์ยังต่ำ แบบนั้นมันแสดง brief แล้วรอคุณตอบ `ทำ`

## ราวกั้นความปลอดภัย

- **push ถูกกันที่ระดับ git** `pre-push` hook ตั้งผ่าน git environment ของ process worker จึงมีผลทุก worktree ของ repo รวมถึงตัวหลัก ให้ worker push ได้เฉพาะ branch `<ชื่อ agent>/<slug>` ของตัวเอง ref อื่นทั้งหมด (develop, uat, main) และการลบ branch บน remote ต้องรอ gate `push`
- **gate อื่น** คือ `shared-write` และ `delete` เป็น deny rule ในไฟล์ settings ที่สร้างใหม่ทุก turn การอนุมัติมีผลแค่ turn เดียว
- **production ไม่มี gate** อนุมัติผ่านการส่งงานไม่ได้เลย คุณ deploy production จาก session ของคุณเองเท่านั้น
- **ไม่เชื่อคำพูดของ worker** commit นับจาก `git log` ไม่ใช่จากที่ worker บอก รายงานที่อ่านไม่ได้ไม่มีวันนับว่า "เสร็จ"
- **มี turn ตรวจ** turn ที่บอกว่าเสร็จจะได้อีกหนึ่ง turn ก่อนรายงานถึงคุณ ถ้าแก้ไฟล์ UI แต่ไม่ได้กดจริง หรือแก้โค้ด (ไม่นับ test และ type) แต่ไม่ได้ลอง input จริง เพราะกฎที่เขียนเป็นข้อความไม่พอจะกัน UI ที่ไม่มีใครกดไม่ให้ถึงมือคุณ
- **จำกัดจำนวน** งานรันพร้อมกันได้ไม่เกิน `maxRuns` (ค่าเริ่ม 3 ตั้งได้ 1-20 ด้วย `bun twin.ts profile maxRuns=<n>`) งานที่เกินจะถูกปฏิเสธพร้อมบอกวิธีเพิ่ม
- **secret** worker ได้เฉพาะ secret ที่ brief ระบุในบรรทัด `secret:` engine ตั้งเป็น environment variable ตอนเริ่ม turn การอ่าน secret store เองถูกห้ามไว้ แต่เป็นแค่เนินชะลอ ไม่ใช่กำแพง

## ความลึกของการรีวิว

บรรทัด `ขนาด` ใน brief ไม่ได้บอกขนาดของ repo แต่บอกว่า worker ต้องรีวิวแค่ไหน

| ขนาด | รีวิว |
|---|---|
| เล็ก | ไม่มีรีวิว |
| กลาง | reviewer อิสระหนึ่งตัวดู diff สุดท้าย |
| ใหญ่ | reviewer อิสระหนึ่งตัวดู diff สุดท้าย |

reviewer ไม่ใช่ตัวที่เขียนงาน ถ้ามี pstack ใช้ review agent ของ pstack ถ้าไม่มีใช้ subagent อีกตัว ไฟล์เดียวที่ตรวจได้ตรงๆ คือ เล็ก แม้ใน repo ใหญ่ ส่วน release หรือของที่คนอื่นติดตั้งหรือซื้อคือ ใหญ่ แม้ diff จะเล็ก

สัญญาของ worker ยังมีกฎ input ด้วย worker ต้องลอง input ที่ brief ไม่ได้บอก เช่น ค่าว่าง ศูนย์ ติดลบ ทศนิยม ค่าใหญ่มาก รูปแบบผิด ชนิดผิด และค่าซ้ำ แล้วตัดสินว่าแต่ละค่าควรได้อะไร กฎนี้มาจากการวัดที่พบว่า worker ทุกแบบรายงานว่างานแบ่งบิลเสร็จโดยไม่ได้ตรวจ input ดู[เหตุผลของการออกแบบ](/th/docs/design#การส่งงาน)

## ตามงานและปิดงาน

| คุณพูด | agent รัน |
|---|---|
| ok push / push เลย / เข้า main | `bun twin.ts followup <id> --approve push "…"` ตามขั้นตอนลงงานใน `CLAUDE.md` ของโปรเจกต์ |
| ตอบคำถาม หรือสั่งงานเพิ่ม | `bun twin.ts followup <id> "<คำของคุณ>"` |
| แก้วิธีทำงานของ worker | followup พร้อมให้เพิ่มกฎนั้นลง `CLAUDE.md` ของโปรเจกต์ |
| ปิดงาน | `bun twin.ts close <id>` |

- followup ที่ส่งตอน worker ยังทำอยู่จะเข้าคิว และเริ่มทันทีที่ turn ปัจจุบันจบ ถ้าจะหยุดตอนนี้ ใช้ `close --stop` เท่านั้น
- `close` ลบ worktree และ branch ในเครื่อง และปฏิเสธถ้ามี commit ที่ยังไม่ push ใช้ `--discard` เมื่อคุณบอกว่าทิ้งเท่านั้น
- งานที่ branch merge เข้า develop, uat หรือ main แล้วปิดได้โดยไม่ต้องถาม และ `daily` ปิดให้ทุกเช้า
- worker ไม่เปิด PR เอง ถ้าโปรเจกต์ใช้ PR agent เปิดให้หลังคุณอนุมัติ push
- จะเข้าไปทำต่อเองด้วยมือ ใช้บรรทัด `takeover:` จาก `bun twin.ts runs` ซึ่งคือ `claude --resume <id>` ใน worktree

## งานกับ session

เมื่อเปิดคุยหลายหน้าต่าง งานเป็นของ session ที่ส่งมันไป `runs/` ยังแชร์กันทุก session เพื่อให้ทุกหน้าต่างเห็นงานที่รอคุณ แต่ brief และ `runs` แสดงงานของหน้าต่างอื่นเป็น `session อื่น`

- `followup` และ `close` ปฏิเสธงานของ session อื่นที่ยังเปิดอยู่ ใช้ `--take` หรือ `bun twin.ts take <id>` เพื่อย้ายมาที่นี่ ปุ่ม **… here** บนแถบสถานะทำแบบนี้ให้
- session ที่ปิดไปแล้วไม่ได้เป็นเจ้าของอะไร followup ถัดไปจากที่นี่รับงานนั้นมาเลย เพราะคนที่ใช้แค่ Desktop ย้อนกลับไป session เก่าจากเทอร์มินัลไม่ได้
- งานที่ไม่มีเจ้าของ เช่น plan ตอนเช้าที่ตารางเวลาเริ่มให้ เปิดให้ทุก session และ session แรกที่ followup จะเป็นเจ้าของ
